### 🔹 Tech1技术一面（共4轮）
#### 第1轮
**面试官（Tech1）**：
在你的 RepoMind 项目中，提到了基于 AST 的多级分块策略来提取代码结构元数据。我想了解一下，在具体实现层面，你是使用 Python 自带的 `ast` 模块还是第三方库（如 `tree-sitter`）？如果是处理跨文件的函数调用关系（call relationships），你是如何解析依赖图的？另外，在索引构建阶段，AST 解析的开销是如何评估和优化的？

**候选人回答**：
RepoMind项目中，我们采用了混合方案：Python代码用标准ast模块解析，Java/C++/Go等12种语言用tree-sitter实现跨语言AST解析，封装了统一的AST遍历接口抹平不同语言的节点结构差异。跨文件函数调用关系解析我们做了两层处理：第一层是静态依赖索引，首先解析每个文件的import语句构建全局符号表，记录函数/类的定义位置、签名、导出情况；第二层是调用关系提取，遍历每个函数体中的调用表达式，匹配全局符号表中的定义，构建完整的跨文件依赖图。AST解析开销的优化主要做了三点：1）增量解析：只解析git diff变动的文件，不需要全量重解析；2）多线程并发解析：按文件粒度并行处理，解析速度提升3倍以上；3）缓存机制：解析结果按文件哈希缓存，相同文件不需要重复解析。最终单项目10万行代码的解析耗时控制在2秒以内。

#### 第2轮
**面试官（Tech1）**：
刚才你提到了多线程并发解析，我想追问一下：在多线程解析同一个项目时，如何避免符号表的并发写入冲突？是用全局锁还是做了更细粒度的并发控制？如果多个线程同时解析同一个被依赖的公共文件，会不会导致重复解析？

**候选人回答**：
我们采用了"先查缓存+乐观锁"的并发控制策略：首先每个线程解析文件前先查全局缓存，如果已经有解析结果就直接复用，避免重复解析；如果缓存没有，就尝试获取该文件的独占锁，只有抢到锁的线程才会执行解析，其他线程等待解析完成后直接拿缓存结果。全局符号表的写入用细粒度的分段锁，按文件路径哈希分成16个分段锁，不同路径的文件写入不会冲突，解析性能损失控制在5%以内，不会有锁竞争问题。

#### 第3轮
**面试官（Tech1）**：
了解了。你提到的AST分块策略，对于Python这种动态语言，函数可以在运行时动态修改、类可以动态添加属性，静态AST解析会不会无法捕获这些动态行为？这种情况你们是如何处理的？

**候选人回答**：
确实纯静态AST解析无法覆盖动态行为，我们做了两层补充：第一层是动态插桩采集，对于Python项目在运行测试用例时插桩采集实际运行时的函数调用关系、动态属性等信息，补充到静态索引中；第二层是用户标注机制，支持用户通过特殊注释标记动态生成的类和函数，AST解析时会识别这些注释纳入索引。两种方式结合，动态场景的覆盖度可以提升到90%以上，满足大部分使用需求。

#### 第4轮
**面试官（Tech1）**：
非常好。现在进入coding环节，请你实现一个函数，判断一个整数数组中是否存在重复元素，要求时间复杂度O(n)，空间复杂度O(1)，不需要修改原数组。

**候选人回答**：
可以用快慢指针的龟兔赛跑算法，把数组看成特殊的链表，每个位置的值就是下一个节点的索引，重复元素就是环的入口点。具体实现：
```python
def find_duplicate(nums):
    slow = fast = 0
    while True:
        slow = nums[slow]
        fast = nums[nums[fast]]
        if slow == fast:
            break
    slow = 0
    while slow != fast:
        slow = nums[slow]
        fast = nums[fast]
    return slow
```
这个算法时间复杂度O(n)，空间复杂度O(1)，不需要修改原数组，符合要求。

### 🔹 Tech2技术二面（共4轮）
#### 第5轮
**面试官（Tech2）**：
关于增量解析的缓存失效策略，你提到只解析 git diff 变动的文件。但在跨文件依赖场景中，如果文件 A 修改了一个被文件 B 引用的函数签名，而文件 B 本身没有代码变动，你的全局符号表如何感知到文件 B 的索引已失效？这种传递性依赖的失效追踪开销如何控制，会不会在极端情况下退化成全量重建？

**候选人回答**：
我们通过反向依赖索引解决传递性失效问题：在构建全局符号表时，每个函数/类符号会额外维护一个"被引用文件列表"，记录所有引用了该符号的文件ID。当文件A修改了函数签名时，首先更新该符号的被引用列表，将列表中的所有文件标记为"待更新"，只重新解析这些受影响的文件，不需要全量重建。开销控制主要做了两点：1）层级依赖剪枝：只标记直接引用，不会递归标记，因为函数签名的依赖，避免级联深度控制在1层；2）批量延迟更新：将所有待更新文件收集到队列，延迟到索引提交前批量处理，避免零散修改合并更新，1000个文件的项目中，单次修改平均只需要重新解析3-5个文件，不会退化成全量重建。

#### 第6轮
**面试官（Tech2）**：
那如果出现A→B→C的链式调用，C修改了函数签名，导致B的输出结构变化，B的接口签名没有变，但是返回值的结构变了，A依赖B的返回值结构，这种情况你们的反向索引就检测不到了吧？这种间接的结构变更怎么处理？

**候选人回答**：
这种场景确实无法通过静态依赖索引检测到，我们通过三种方式补偿：1）函数签名不仅包含参数列表，还包含返回值的类型结构，如果函数返回值结构变化，会更新签名哈希，触发所有引用该函数的文件更新；2）静态类型分析，通过Type Hint或者类型推断得到返回值结构，发生变化时触发依赖更新；3）单元测试门禁，代码提交时运行单元测试，如果依赖该接口的测试用例失败，会自动触发相关文件的索引重建，弥补静态分析的不足。

#### 第7轮
**面试官（Tech2）**：
那你们的索引系统和CI/CD流程是怎么集成的？代码提交时会不会自动更新索引，会不会影响CI速度？

**候选人回答**：
我们做了增量CI钩子，代码提交时只解析diff变动的文件，更新增量索引，全量重建放在凌晨低峰期自动运行，单次提交的增量解析耗时控制在10秒以内，不会影响CI速度。同时支持开发本地增量更新，开发人员在本地修改代码后可以实时更新本地索引，不需要等CI构建。

非常好。现在问一个系统设计问题：如果要把RepoMind做成SaaS服务，支持十万级用户、百万级代码仓库，你会怎么设计架构？

### 🔹 系统设计面（共3轮）
#### 第9轮
**面试官（架构师）**：
你的‘层级剪枝控制在 1 层’策略在性能上很有吸引力，但在架构正确性上我有个顾虑：假设存在 A→B→C 的调用链，若 C 的变更导致 B 的对外签名也发生变化，理论上 A 也需要更新。如果只标记直接引用，是否会漏掉这种传递性签名变更？在这种‘性能优化’与‘索引完备性’的 Trade-off 中，你们的降级策略或补偿机制是什么？

**候选人回答**：
我们通过三重补偿机制平衡性能与正确性：1）兜底全量校验：每天凌晨低峰期自动运行一次全量依赖校验，修复白天增量更新可能遗漏的传递性变更，确保索引最终一致性；2）变更影响分析预警：针对核心路径的符号修改，我们会运行全量依赖分析，标记所有潜在受影响文件，不受层级限制；3）用户主动触发机制：提供强制全量重建接口，用户可随时触发全量索引更新。同时我们设置了监控指标，当搜索结果召回率低于阈值时，自动触发全量重建，保证在极端场景下不会影响用户体验。在实际应用中，1层剪枝已经覆盖了99%的场景，剩余1%通过上述机制兜底，兼顾了99%场景下的性能和1%异常场景的正确性。

**候选人回答**：
我们做了并行优化，百万行代码的全量校验运行一次大约5分钟，放在凌晨低峰期运行，优先级设为最低，不会影响线上服务。同时支持增量校验，只校验最近24小时有变更的文件及其依赖，耗时可以控制在30秒以内，也可以在白天运行。

#### 第11轮

如果用户自定义了剪枝层级，比如有些用户要开3层剪枝，你们怎么处理不同用户的差异化配置？会不会导致索引冲突？
